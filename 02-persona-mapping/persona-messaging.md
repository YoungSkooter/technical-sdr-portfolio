# Persona Messaging Matrix

## Outreach Principle

Do not begin with:

> "We provide an AI-powered security platform..."

Begin with an observable technical context and a question.

---

| Persona | Technical Context | Problem Hypothesis | Opening Angle |
|---|---|---|---|
| Security Engineering | Security investigation | Manual context gathering | Investigation workflow |
| Cloud Security | AWS/cloud findings | Prioritization + context | Finding investigation |
| Platform Security | Kubernetes/platform | Security-to-platform handoff | Remediation workflow |
| Security Operations | SIEM/alerts | Manual triage | Alert investigation |
| Platform Engineering | Infrastructure remediation | Security workflow friction | Engineering handoff |
| Security Leadership | Security operations | Engineering capacity | Automation / efficiency |

---

# Primary Persona

## Security Engineering

### Hypothesis

Figma has invested heavily in security investigation automation. There
may still be investigation workflows where engineers need to manually
gather context.

### Message Direction

> "Saw the work your security team has been doing around automating
> alert investigation. Curious — where do engineers still have to
> manually pull context together before they can determine what needs
> to happen?"

### Why This Works

It:

- references a real public signal
- demonstrates research
- doesn't pretend to know their pain
- doesn't immediately pitch a product
- asks about a technical workflow
- gives the prospect room to correct the hypothesis

# Messaging Rules

### Rule 1 — Research before personalization

Bad:

> "I noticed Figma is a fast-growing SaaS company."

Better:

> "I saw Figma's recent work around automating security alert
> investigation..."

---

### Rule 2 — Hypothesis, not accusation

Bad:

> "Your security team wastes hours investigating alerts."

Better:

> "Curious where investigation still requires manual context gathering."

---

### Rule 3 — Workflow before product

Bad:

> "Our platform integrates with AWS and Kubernetes."

Better:

> "How does your team currently connect a security finding with the
> context needed to determine ownership?"

---

### Rule 4 — Technical specificity

Generic:

> "How are you handling cybersecurity?"

Specific:

> "When a cloud-security finding requires additional investigation,
> what systems does the engineer typically have to pull context from?"

---

### Rule 5 — Leave room to be wrong

The prospect should be able to say:

> "Actually, we've already automated most of that."

That is a useful answer.

The SDR can then ask:

> "Interesting — what's still outside the automated workflow?"
