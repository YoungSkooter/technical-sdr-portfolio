# Lessons Learned

> **PORTFOLIO REFLECTION — SIMULATED PROJECT**

---

# 1. Research Does Not Equal Qualification

Finding a company with:

- AWS
- Kubernetes
- Security Engineering
- Cloud Security

does not prove that it needs a product.

Research creates a hypothesis.

Conversation creates evidence.

---

# 2. Technical Knowledge Is a Means, Not the Goal

Knowing Kubernetes, AWS, IAM, security monitoring, or cloud architecture is useful because it allows the SDR to:

- Understand the prospect's environment
- Ask better questions
- Recognize technical signals
- Avoid embarrassing technical misunderstandings
- Communicate effectively with technical buyers
- Give the SE better context

The SDR does not need to replace the SE.

---

# 3. Discovery Is About Workflow

A vague question:

> "Do you have cloud-security challenges?"

produces weak information.

A workflow question:

> "When a complex cloud-security alert requires additional context, where does that context come from?"

can reveal:

- Systems
- People
- Manual steps
- Ownership
- Automation
- Bottlenecks

---

# 4. Objections Are Information

"We already have a SIEM."

"We built this internally."

"We already automated that."

"We're happy with our current tooling."

These aren't merely barriers.

They reveal the customer's current state.

---

# 5. Meetings Are Not the Finish Line

A meeting is an event.

A qualified opportunity requires evidence.
